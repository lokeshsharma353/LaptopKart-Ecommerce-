1. Executive Summary

TechBasket is a customer-facing laptop storefront built on Salesforce Experience Cloud using the Build Your Own (LWR) template. It is composed entirely of custom Lightning Web Components backed by custom Apex, and it writes into the organisation's existing Enterprise Order Management data model rather than a parallel one.

2. Technology Stack & Architecture

LayerTechnology
PlatformSalesforce Experience Cloud — Build Your Own (LWR) template
UI frameworkLightning Web Components (LWC), HTML, CSS, JavaScript — no external frameworks
BackendApex classes (@AuraEnabled), Apex triggers, existing handler/service classes
DataStandard objects (Account, Contact, Lead, Opportunity, Order, OrderItem, Product2, PricebookEntry) plus custom objects Payment__c and Order_Tracking__c
Client-side stateBrowser localStorage via shared JavaScript service modules (cart, checkout draft, wishlist)
DeploymentSalesforce CLI (sf project deploy start) from a local SFDX project

Architectural principles applied

  • No SOQL or DML inside JavaScript. All data access goes through Apex.
  • Server-side pricing. Checkout re-reads prices from PricebookEntry — prices sent from the browser cart are never trusted, preventing price tampering.
  • Reuse over rewrite. Existing Order/Payment/Tracking automation is triggered, not duplicated.
  • No invented fields. Every field referenced was verified against the org's actual schema first.
  • Centralised logic. Navigation, cart maths, and toast messaging each live in exactly one module.

9. Known Issues

9.1 Cart empties between Checkout and Payment — confirmed, blocking

Symptom: Completing Checkout and moving to Payment shows "Your cart is empty".

Root cause: The browser's address bar changes domain between those two pages. localStorage is scoped per domain, so the cart and checkout draft written on one domain are invisible on the other.

Fix path: Publish the site so all recently added pages are served from the same domain, and test the whole journey from one canonical URL. If the split persists, the cart must move from localStorage into a server-side store, which is a larger change.

9.2 Payment method values do not match the picklist — will fail

The UI sends internal keys (card, upi, emi…) into Payment_Method__c, which only defines Cash, Card, Net Banking. Values must be mapped properly and the required new values added.

9.3 Shipping and tax are not represented in Salesforce — by design, needs decision

Order.TotalAmount is a roll-up of OrderItems only. Shipping and tax shown on the website have no line-item representation, so the Payment record is deliberately created for the product subtotal only. Website total and Salesforce total therefore differ.

9.4 Order History relies on browser memory — temporary

Order History shows orders whose IDs this browser remembers, not orders belonging to the logged-in customer. Now that real login exists, this should query by the authenticated Contact.

9.5 Smaller gaps

  • Sign-up and login have not been verified in a live browser session.
  • contactTrigger is an empty shell.
  • authService and mockProductData are dead code.
  • Ratings, stock levels and discounts were removed from product pages because no such fields exist on Product2.

11. Security & Compliance Notes

11.1 Storing passwords on the Account object

This requirement should not be implemented as specified. Storing a customer password in a custom field — even one hidden from most profiles — means the password is held in plain text. It would be readable through the API, reports, debug logs, data exports, backups, and by any Apex running in system context. Field-level security does not prevent any of that. A single exported report or log file would expose every customer's password, and because people reuse passwords, the damage would extend beyond this site.

Recommended instead: Salesforce's own Experience Cloud authentication, which is already partially in place. It stores passwords hashed and salted, never exposes them to anyone including administrators, and provides password reset, lockout policies and expiry for free. Administrators still see the customer as an ordinary Contact/Account record, which is the visibility you wanted. The only capability genuinely lost is an administrator being able to read a customer's password — which is precisely the property that makes it safe.

11.2 Product and background imagery

The requirement asks for real product photographs and high-resolution background images taken from the internet. Images found online are usually copyrighted. Before publishing, images should come from one of: official brand/manufacturer media kits with permission, a licensed stock library, or photographs you own. This matters more once the site is publicly published.

11.3 Payment handling

Card number and CVV are currently held only in component memory during entry, are never sent to Apex, and are never stored or logged. This is correct and should be preserved. Real payment processing still requires a payment gateway integration; the current flow simulates authorisation.
