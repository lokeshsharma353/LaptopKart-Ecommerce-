1Discount Campaigns & Coupon Codes

Standard Campaign stands in for "Diwali Offer 2026" — Name, StartDate, EndDate, IsActive, Description all map directly. A coupon code (e.g. DIWALI10) is a new object, Master-Detail to that Campaign. Every redemption is logged on standard CampaignMember, extended with 3 fields, rather than a new custom ledger object — every checkout already produces a real Contact, and CampaignMember exists purely to link a Contact to a Campaign.

Assumption made explicit "One code is valid only one time for the users" is read here as per customer — DIWALI10 can be used once by every customer, not once total across the whole store. If you meant a single global use (first customer only), that's a one-line change to the validation query in Build Order step 4.

2Loyalty Points

One live number per customer and one ledger (Loyalty_Point_Transaction__c) that logs every earn and redeem — the same pattern §1's coupon ledger uses. The balance lives on standard Account (Customer Account Detail record type, per the Account consolidation decision) — no standard object covers a points ledger, so the transaction log stays a new custom object.

Assumption made explicit "1 point when order someone" is read as 1 point per ₹1,000 spent, earned once the order is actually Fully Paid — not at the moment of placing the order — since Cash on Delivery orders shouldn't earn points before the cash is collected. The redemption value (how much ₹1-off 1 point is worth) is listed as an open decision below.

3GST / Tax System, and Fixing Billing vs Shipping Address

What the audit found — not a design choice, a real gap CheckoutController.CheckoutInput has no billing-address fields at all — only shippingStreet/City/State/PostalCode/Country. The Billing Address form already exists in the UI (techBasketBillingForm) and the shopper's input is held in techBasketCheckout's draft — but techBasketPayment.js's completeOrder() builds the Apex payload from this.draft.shippingAddress only. this.draft.billingAddress is read nowhere. The standard Order.Billing* fields exist on the object but are simply never set. This has to be fixed as part of this feature — a GST invoice legally needs a real billing address.

India's GST is place-of-supply based for physical goods: the split between CGST+SGST (intrastate) vs IGST (interstate) is decided by comparing the seller's registered state to the shipping (delivery) state — not the billing state. Billing address is what's printed on the invoice as who is being billed; it can legitimately differ from where goods ship, and doesn't change the tax split. Each product carries its own GST rate (laptops are typically the 18% slab, but this varies by HSN code, so it's a per-product field).

  4. TaxService.cls logic — given cart lines and the shipping state, computes taxable amount and the CGST/SGST vs IGST split.
  5. Order Summary / Payment (LWC) logic — itemize CGST + SGST (or IGST) in the totals panel, not a single "tax" line.
  6. Invoice PDF logic — add the tax breakdown and the now-real billing address to OrderInvoiceController's output.

Decisions only you can make

  • Seller's registered state: what is it? (A Custom Setting/Metadata Type record, not a hardcoded constant, so it's editable without a deploy.)
  • Tax-inclusive or exclusive pricing: do storefront prices already include GST (common in Indian B2C), or is GST added on top at checkout?

5Ordering On Behalf Of Someone Else, and "Show All My Orders"

What the audit found There is currently no link between an Order and the shopper's login identity at all — submitOrder doesn't even receive a login/session id as a parameter. The only tie between a shopper's login identity and "their" orders is getOrdersByEmail(email), matched by the email typed at checkout. So today, a logged-in shopper who ships to a different email would find that order missing from their own Order History — there's no record of who actually placed it, only who it's addressed to.
Assumption made explicit — original wording was ambiguous Add a Placed_By__c lookup on Order that always stores the actual logged-in Account (Customer Account Detail record, per the Account consolidation decision) that submitted the order — separate from Customer_Name__c and the shipping fields, which describe who the order is for. "Show all the orders" is read as: My Account's Order History should list every order a shopper has ever placed, which it can't do today.

Object reference

Ordernew fieldExtend
Placed_By__cPlaced ByLookup(Account)The logged-in Account (Customer Account Detail) that actually submitted the order — distinct from the standard AccountId field, which is who the order is for

Build order

  1. Order.Placed_By__c schema
  2. CheckoutController.submitOrder logic — add accountId to CheckoutInput (the LWC already has it via the logged-in session), set orderUpdate.Placed_By__c in STEP 7.
  3. getOrdersByAccountId(accountId) logic — new @AuraEnabled method, alongside (not replacing) getOrdersByEmail.
  4. Checkout (LWC) logic — the "For myself / For someone else" toggle and second recipient form.
  5. Order History (LWC) logic — use getOrdersByAccountId so every placed order shows up, not just email matches.

Decisions only you can make

  • Should an order placed for someone else also be visible to that recipient if they separately have their own account, or only to whoever placed it?
  • Any limit on how many "for someone else" orders one account can place (fraud consideration), or fully open?

6Cart System — Audit Findings & Fix Plan

What the audit found — this is a bug fix, not a new feature Cart_Items__c (moving to Account under the Account consolidation decision) is write-only. cartService.js writes to it on every cart change and the instant a login session starts — but nothing anywhere reads it back. Confirmed directly: cartService.js's getCart() reads exclusively from localStorage; the login controller's logIn/signUp don't even SELECT Cart_Items__c; techBasketMyAccount.js's login handler doesn't import cartService at all. The practical effect: logging into the same account on a new device or a cleared browser always starts with an empty cart, even though Salesforce has been faithfully mirroring the cart the whole time.

Object reference

No schema change needed — Cart_Items__c already exists (on Account per the consolidation decision) and is already being written correctly. This is purely an Apex + LWC fix.

Build order

  1. Login controller's logIn / signUp logic — add Cart_Items__c to the SOQL against Account, add a cartSnapshot field to the session return type.
  2. cartService.js logic — new exported restoreOrMergeCart(cartSnapshotJson) implementing the merge-vs-replace logic above.
  3. techBasketMyAccount.js logic — call restoreOrMergeCart with the returned snapshot right after login succeeds, before setSession fires.

Decisions only you can make

  • Merge vs. replace: if the browser already has cart items at login, should the account's saved cart merge with them, or replace them outright? Merge is friendlier but can surprise someone on a shared/public computer.
