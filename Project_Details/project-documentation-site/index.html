Pricing, Discount & Loyalty Engine

The single, authoritative pricing calculation — OrderPricingService.calculate() — used identically by the live cart/checkout preview (CheckoutController.previewOrderTotals) and the real charge (CheckoutController.submitOrder). Nothing about a coupon, a loyalty redemption, or a shipping cost is ever trusted from the browser: every one of those is re-derived from Salesforce data on every single call, using only an id/code the client supplies.

Worked example

A ₹25,000 laptop (default 18% GST, no category-restricted coupon), Delhi delivery address (intrastate), Overnight shipping selected.

Permissions & Sharing Model

Every access-control mechanism this project actually uses, read directly from the deployed metadata: org-wide sharing defaults, the Guest-checkout sharing rules, the public group they share to, the two admin permission sets with their exact field grants, and the Apex-level sharing pattern every controller follows.

Why this is more layered than a typical org

Most of the checkout pipeline runs as the Guest User — an unauthenticated visitor has no meaningful permissions of their own, so almost every Apex class is declared without sharing and queries WITH SYSTEM_MODE (full object/field access, sharing rules ignored) to get real work done. The sharing rules and permission sets below exist for the second half of the story: once a Guest-created record is reassigned to the admin user at the end of checkout, something still has to let that Guest read it back later (their own order confirmation, tracking, invoice) without SYSTEM_MODE — that's what the sharing rules are for.

Org-Wide Defaults

Set to Private on every object the checkout pipeline touches — required before an owner-based sharing rule can grant anything on top.

Group membership for the Site Guest User isn't metadata-deployable. The Laptop_Kart public group itself deploys cleanly (it's just a name), but adding the site's actual Guest User as a member of it has to be done by hand in Setup → Public Groups → search "Site Guest User" → Add — there's no supported metadata type for Guest User group membership. Skipping this step leaves the sharing rules deployed but functionally inert: correct on paper, granting nothing in practice.

Guest User Profile

Auto-generated the moment the Digital Experiences site is created (one per site, named after it) — Laptop Kart Profile in the original build org, LaptopKart Profile in the migrated personal org, both carrying userLicense: Guest User License.

Its real object/field permissions aren't retrievable through the Metadata API at all. Every attempt to pull this profile back down returns just <custom>true</custom><userLicense>Guest User License</userLicense> — five lines, no objectPermissions, no fieldPermissions. The Guest User's actual access for an LWR site is configured through Experience Builder → Administration → Preferences (Public Access Settings), a separate UI surface from classic Profile editing, and it doesn't round-trip through source control the way every other permission on this page does.

Apex sharing pattern

A consistent, deliberate split across the whole codebase, not ad hoc per class.

PatternUsed byWhy
without sharing + WITH SYSTEM_MODECheckoutController, DiscountService, LoyaltyService, InventoryService, OrderPricingService, LoginCredentialsController, ContactController, WelcomeLeadController, OrderTrackingService, PaymentService — every Guest-facing controllerThe Guest User has no meaningful record access of its own; SYSTEM_MODE bypasses both object/field security and sharing so the checkout pipeline can actually create Leads/Accounts/Orders/Payments end to end
with sharing + WITH USER_MODEOrderPaymentController (the internal Order-record-page dashboard)Runs as a real logged-in internal user viewing a record they already have access to — no reason to bypass their own permissions here
without sharing (WITH SYSTEM_MODE queries)OrderInvoiceController, AdminDashboardControllerInvoice PDF rendering and the admin dashboard both need to see every record regardless of who's viewing, without requiring a full sharing-rule setup for every query they run

External system access

Razorpay (payment gateway): a Named Credential/External Credential Principal named Razorpay, referenced in Apex only as callout:Razorpay — the API secret is stored by Salesforce and never appears in Apex, the browser, or version control. Like the Guest Profile above, the secret value itself is not retrievable or deployable through metadata; moving this integration to a new org means re-entering it by hand in Setup → Named Credentials every time. See Changelog for the exact scenario this hit.

Changelog & Deployment

What changed in the most recent deep audit pass, and where this project now actually runs.

Fixes shipped 2026-09-18/19

Found via a from-scratch functional audit, each verified with real Apex assertions or a full regression run before being marked done.

  1. Shipping cost was never charged, on any order, ever

    OrderPricingService.calculate took no shipping parameter at all — the real, server-computed amountPayable (the figure actually charged via Razorpay, verified, and stored) never included it, regardless of Standard/Express/Overnight being selected. Added Shipping_Cost__c / Shipping_Method__c on Order, a server-side method-id→price lookup mirroring the client's own list (never trusts a client-supplied amount), and wired it through the preview, the real charge, the Razorpay payment-link amount, the confirmation email/page, and the invoice.

  2. The downloadable invoice PDF showed the wrong total — on every order

    OrderInvoiceController.getBalanceDue used raw Order.TotalAmount (the pre-tax, pre-discount product sum) instead of the real Amount_Payable__c. The Cash-on-Delivery "keep ₹X ready" notice used this same understated figure, meaning every COD customer was told to have less cash ready than they actually owed — short by the full 18% GST, and now shipping too. Fixed to show a full Subtotal → Discount → Taxable Value → GST → Shipping → Amount Payable → Paid → Balance Due breakdown.

  3. Checkout's own sidebar never reflected the shipping method you'd clicked

    The Shipping Method step only told its parent what was selected when "Next" was pressed, not live as you compared options. Now techBasketShippingMethod emits on every click (and once on load for the default), so the sidebar total updates immediately — before you've committed to a choice.

  4. Cart/Checkout showed a placeholder 5% tax instead of the real 18% GST

    Every one of the 54 real products in the catalog falls back to the 18% default GST rate (none override Product2.GST_Rate__c), but the pre-checkout estimate in cartCalculations.js used a hardcoded 5% — a roughly 5× understatement of tax on every cart view before Payment loaded the real figure. Corrected the constant to match.

  5. Quantity selectors had no real stock ceiling

    On Product Detail, the Cart page, and the mini-cart drawer, the +/− control defaulted to a flat cap of 99 regardless of actual Stock_Quantity__c — a shopper could select 10 of an item with 2 left and only find out at the very last step of checkout (server-side InventoryService.validateStock would reject it). All three now enforce the product's real tracked stock live.

What can't move via metadata, and why

Two genuine Salesforce platform restrictions hit during the org-to-org migration, confirmed directly by the platform's own errors rather than assumed — documented here so they don't need rediscovering.

An LWR Experience Cloud site can't be originated from metadata at all. Retrieving the underlying Picasso/SiteDotCom component for a "Build Your Own (LWR)" site returns, verbatim: "A SiteDotCom site using template [Build Your Own (LWR)] does not support MD API Retrieval." Digital Experiences must be enabled and the site shell created through the Setup UI wizard first — only its content (DigitalExperienceBundle: every page, the theme, styles, branding) can be retrieved and deployed afterward, which is what actually moved between orgs here.
Named Credential secret values never travel through metadata, by design. The Razorpay integration's API secret (stored in a Named Credential / External Credential Principal) has to be re-entered by hand in Setup on every org it's deployed to — there is no metadata type that carries the secret value itself, in this org or any other.
Also genuinely unfixable via metadata: the "Cancelled" value for Order.Status (a standard, restricted picklist) isn't independently retrievable or deployable through any metadata type — there's no StandardValueSet:OrderStatus, and the field's own CustomField metadata carries no value-set definition at all. Adding it to a new org means Setup → Object Manager → Order → Fields & Relationships → Status → New, by hand, every time.
